## Requirements for another backend

An additional renderer should extend the current compiled contract instead of duplicating the older static parent/child example:

1. Keep domain transitions, keyed identity, generations, and `View` construction in Go. Build the same package through the existing compiler and use its manifest-provided AppIR, encoder, and compiled module. Do not add JavaScript application state.
2. Advertise `view.node` and support the existing renderer API (`update`, `viewRecord`, `domSnapshot`, `unmount`) plus `effect.request-reply` and `effect.cancel`. Compatible swaps must preserve the mounted runtime, Go state, pending correlations, and active callbacks. Reject an incompatible candidate without retiring them.
3. Replay the same fixed and bounded seeded keyed-child scenarios through native Go, direct compiled execution, and mounted browser controls. Compare complete typed state, Gobi trees, ordered effects/messages, DOM/control captures, reorder and reuse identity, disabled behavior, reverse cancellation, stale callback fencing, and accepted/rejected swaps. Use real browser actions for renderer behavior claimed as observed.
4. For the next application feature, apply PR13’s typed parent-input and child-publication contracts to dynamically keyed child identities: live immediate-parent input admission with monotonic revisions; child publication of Go-captured saved values at the current revision into the immediate parent’s ordered inbox; and stale/deleted/recreated child isolation. Preserve the source contract’s rejection-without-mutation, ordering, and renderer-refresh requirements. Do not repeat the existing static child case as if it proved dynamic-key behavior.
