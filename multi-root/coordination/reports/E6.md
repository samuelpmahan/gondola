# E6 — demo, runner, CI, and delivery evidence

## Implementation

`multi-root/demo.html` and `multi-root/demo.mjs` present three simultaneous Go
collection sessions using DOM, React, and GoDOM. Each panel exposes its Go
session ID, a fresh HTTP lane, renderer-local swap controls, request records,
Go snapshot/audit data, transport events, and live DOM/focus. The demo can hold
saves from multiple roots, dispose one root with work pending, inspect the
cancelled lane, attempt a late release (the HTTP lab rejects it with 409),
continue using a sibling root, and remount the retired slot.

`run-multi-root.sh` runs `run-renderer-conformance.sh` first on every default
invocation. Only after that full inherited chain succeeds does it build the
multi-session and GoDOM WASM binaries, copy the same toolchain's
`wasm_exec.js`, run the bridge smokes, bundle React renderers, run Go tests and
vet, execute the multi-root Node tests, drive the real browser demo, and run
the seeded replay checker. The GitHub Actions workflow installs Go 1.24.x,
Node 22, pinned interaction dependencies, and Playwright Chromium before
invoking the same entrypoint. The root README links to the demo and evidence
status.

`multi-root/RESULTS.md` records the command plan, exact replay report and
mismatch fields, guarantee matrix, and pending status. The coordination
protocol preserves the distinction between the captured native author
allocation, actual work, review starts, and review acceptances.

The browser exercise caught and repaired three delivery issues before its
passing run: the demo bridge adapter now forwards `list()` required by the
composition contract; the browser gate reports startup errors immediately;
and unchanged request records no longer replace their release buttons on
every 250 ms refresh, which had detached a click before event dispatch. The
first packet-local manual build also omitted the WASM target environment and
produced a native executable; both targets were rebuilt with the exact
`GOOS=js GOARCH=wasm` settings used in the default runner before the passing
browser run. The expected HTTP 409 for a late release is recorded separately
from uncaught browser errors.
